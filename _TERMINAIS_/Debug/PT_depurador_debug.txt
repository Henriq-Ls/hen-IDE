## 1.4 Handshake DAP — ordem correta para debugpy --listen

ARQUIVO: _TERMINAIS_/Debug/cliente_dap.py

COMPORTAMENTO ESPERADO:
  Handshake completo sem deadlock, em ordem:
    1. initialize   → aguarda apenas o response (não o evento ainda)
    2. attach       → enviado imediatamente após o response
    3. aguarda initialized event (só emitido pelo debugpy após receber attach)
    4. setBreakpoints
    5. configurationDone → debugpy inicia o script

COMPORTAMENTO ATUAL (BUG / AUSENTE):
  [✓] IMPLEMENTADO — BUG IMP-01 corrigido.
  Antes da correção: o código aguardava AMBOS (response + initialized event)
  antes de enviar attach. O debugpy só emite o initialized event após receber
  o attach → deadlock de 64 s até timeout.

CAUSA RAIZ:
  cliente_dap.py · ClienteDAP._handshake():
  A versão original usava um único loop aguardando os dois sinais ao mesmo tempo
  antes de enviar attach. O debugpy em modo --listen não emite initialized event
  até receber attach — deadlock garantido com a ordem errada.

ONDE IMPLEMENTAR:
  ClienteDAP._handshake(): dois loops separados — o primeiro aguarda só o response
  do initialize; attach é enviado; o segundo aguarda o initialized event.
  Comentário ⚠️ no código alerta futuros devs sobre a ordem correta.

## 2.4 Encerramento seguro — sem "QThread: Destroyed while thread is still running"

ARQUIVO: _TERMINAIS_/Debug/painel_debug.py · _TERMINAIS_/Debug/cliente_dap.py

COMPORTAMENTO ESPERADO:
  Ao fechar a aba ou clicar Parar:
    1. parar() é chamado no ClienteDAP (flag _parar + disconnect DAP).
    2. _encerrar() fecha o socket, termina o processo (terminate → kill) e drena
       stderr — na ordem correta (término do processo ANTES de drenar).
    3. wait(8000) aguarda a QThread terminar antes de chamar deleteLater().
    4. QThread.finished → _ao_thread_finalizada() → deleteLater() (caminho normal).
  Nunca ocorre "QThread: Destroyed while thread is still running".

COMPORTAMENTO ATUAL (BUG / AUSENTE):
  [✓] IMPLEMENTADO — BUG IMP-03 corrigido.
  Antes: stderr.read() era chamado antes de terminate()/kill(). Como o pipe
  permanece aberto enquanto o processo está vivo, o read() bloqueava
  indefinidamente → IDE congelava ao clicar Parar.

CAUSA RAIZ:
  cliente_dap.py · ClienteDAP._encerrar():
  A ordem original era: fechar socket → ler stderr → terminate/kill.
  A leitura de um PIPE aberto de um processo vivo bloqueia até o processo
  fechar o descritor, o que não acontece se terminate() não foi chamado antes.

ONDE IMPLEMENTAR:
  ClienteDAP._encerrar(): ordem correta:
    1. Fecha socket (interrompe _ler_mensagem).
    2. Drena stderr (proc.stderr.read() + close()) — só funciona após
       o processo ter encerrado ou o pipe ter sido fechado.
    Atenção: na implementação atual, o stderr é drenado ANTES de terminate()
    mas o processo já pode estar morto neste ponto (exited/terminated event).
    O terminate/kill só é chamado se proc.poll() is None.
  painel_debug.py · _parar_sessao_atual(): wait(8000) antes de deleteLater().
  terminal_tab_widget.py · fechar_aba(): detecta PainelDebug → _parar_sessao_atual().

STATUS: [✓] IMPLEMENTADO
